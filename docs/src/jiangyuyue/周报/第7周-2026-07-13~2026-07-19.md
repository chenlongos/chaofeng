## 二、关键成果

### 2.1 内核启动机制突破：FIT image + bootm

TGOSKits StarryOS 是 Linux-musl PIE (entry `0xffffffff80000000`)，而非 bare-metal ELF，不能直接用 `go 0x80200000` 跳转启动。需要 DTB 传递硬件信息。

```bash
# 用 mkimage 将内核 + DTB 打包成 FIT image
mkimage -f starryos.its starryos_sg2002.itb

# U-Boot 启动
fatload mmc 0:1 0x82200000 starryos_sg2002.itb
bootm 0x82200000
```

启动成功，Shell 提示符 `root@starry:/ #`，TPU 驱动 `/dev/cvi-tpu0` 正常挂载。

## 三、Python TPU 推理 — 关键技术实现

### 3.1 整体调用链

```
Python 用户代码 (sg2002_tpu 包)
  │  engine = TPUEngine("model.cvimodel")
  │  output = engine(int8_data)
  │  dets = decode_nms(output)
  ▼
libcviruntime.so (Cvitek TPU 运行时库, RISC-V musl)
  通过 ctypes 桥接, 5 个 C API: Init / RegisterModel / GetTensors / Forward / Cleanup
  │  ioctl
  ▼
/dev/cvi-tpu0 (StarryOS 内核 TPU 驱动)
  │  MMIO
  ▼
SG2002 TPU 硬件 (TDMA + TIU, 0.5 TOPS @ INT8)
```

### 3.2 核心设计决策：raw ctypes 方案

板上 Python 3.11 是 RISC-V musl 交叉编译版本，**没有 pip、没有 build 工具链**。在此约束下三种桥接方案对比：

| 方案 | SG2002 上可行性 |
|------|----------------|
| PyBind11 | ❌ 需 C++ ABI 交叉编译，静态链接 > 2MB |
| Cython | ❌ 需交叉编译生成的 .c，依赖 Python.h |
| **raw ctypes** | ✅ 纯 Python，零编译依赖 |

额外考量：RISC-V 64 + musl 上 ctypes 的 `argtypes`/`restype` 存在结构体传参对齐不兼容。最终采用 `ctypes.CDLL` + `struct.unpack` 手动解析 C 指针内容，完全绕过 ABI 风险。

### 3.3 引擎生命周期

核心流程 4 步，与 C/C++/Rust 版本共享同一套 API：

```
RegisterModel        GetTensors          Forward×N           CleanupModel
加载 cvimodel(95MB)   映射 DMA buffer      memmove→Forward→读输出   释放 TPU 内存
     ~2s                 <1ms                 40ms                  <1ms
```

```python
class TPUEngine:
    def __init__(self, model_path):
        _lib.CVI_RT_Init()                              # ① 初始化运行时
        _lib.CVI_NN_RegisterModel(path, byref(model))   # ② 加载模型
        _lib.CVI_NN_GetInputOutputTensors(...)           # ③ 获取张量句柄
        # ④ 解析 CVI_TENSOR struct → 拿到形状 + DMA buffer 地址

    def __call__(self, int8_data):
        ctypes.memmove(self.in_data, int8_data, ...)     # ⑤ 输入拷贝
        _lib.CVI_NN_Forward(...)                         # ⑥ 触发 TPU
        return ctypes.string_at(self.out_data, ...)      # ⑦ 输出拷贝

    def close(self):
        _lib.CVI_NN_CleanupModel(self.model)             # ⑧ 资源释放
```

### 3.4 预处理：双路径设计

**路径 A — 预量化 INT8（快速路径）**：PC 端离线完成 JPEG 解码 + resize + letterbox + CHW planar 转换，板端直接 `load_int8()` 读取原始字节，适合 Benchmark 和批量测试。

**路径 B — 实时 JPEG（C 加速路径）**：板端实时处理摄像头帧，瓶颈在 resize。为此编写了 C 加速库 `preprocess_ops.so` (5.8KB)：

- 双线性插值 resize + letterbox 填充 + RGB→CHW planar 布局转换
- 编译：`riscv64-unknown-linux-musl-gcc -shared -O3 -march=rv64imafdc`
- Python 侧通过 ctypes 调用，与 Pillow JPEG 解码串联

| 预处理阶段 | 纯 Python | C 加速 | 加速比 |
|-----------|----------|--------|--------|
| JPEG 解码 | ~400ms | ~400ms | 1x |
| resize + letterbox + planar | ~11s | **~5ms** | **2200x** |
| **总计** | **~11.4s** | **~0.4s** | **28x** |

### 3.5 TPU Forward 性能

```python
# 一次推理 = memmove(1.2MB INT8 in) + TPU计算 + string_at(168KB FP32 out)
```

| 子操作 | 耗时 | 占比 |
|--------|------|------|
| memmove 输入 (1.2MB) | ~0.8ms | 2% |
| **CVI_NN_Forward** | **~38ms** | **95%** |
| string_at 输出 (168KB) | ~1.2ms | 3% |

Benchmark 验证：Raw Forward 38.2ms (fps=26)，加 memcpy 40.0ms (fps=25)，**memcpy 开销仅 ~2ms，TPU 计算是绝对瓶颈**。

### 3.6 后处理：NMS 去重

TPU 输出 `[1, 5, 8400]` FP32 → 置信度过滤 (thresh=0.5) → 按置信度排序 → IoU NMS (thresh=0.45) → 最终检测框。

v3 缺失 NMS 导致 11 个重复框，v4 实现 NMS 后精准检出 1 框，与 C++/Rust 输出完全对齐 (conf=0.969, box=(261,263,371,377))。

### 3.7 端到端性能总览

| 输入格式 | 预处理 | TPU Forward | 后处理 | **总耗时** | 瓶颈 |
|----------|--------|-------------|--------|-----------|------|
| `.int8` (内存缓存) | <1ms | 40ms | 1ms | **42ms** | TPU |
| `.int8` (SD 卡) | 1.5s | 40ms | 1ms | 1.54s | SD I/O |
| `.jpg` (C 加速) | 405ms | 40ms | 1ms | 446ms | JPEG 解码 |
| `.jpg` (纯 Python) | 11.4s | 40ms | 1ms | 11.44s | Python resize |

**核心结论**：当输入已在内存中，端到端仅 42ms（~24 fps），TPU Forward 占 95%。实现实时推理的最简路径是 PC 端预量化 → 板端内存缓存 → 连续 Forward。
