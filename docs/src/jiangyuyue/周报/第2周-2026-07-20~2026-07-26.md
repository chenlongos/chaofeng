## 二、关键成果

### 2.1 端到端 TPU 推理管线（StarOS 板上实跑）

五段式 Python 管线：摄像头（YUYV 640×480）→ C 预处理（yuyv→CHW）→ TPU Forward → C NMS → 检出。

| 组件 | 耗时 | 备注 |
|------|------|------|
| Camera DQBUF | ~255ms | USB UVC 驱动待优化（李明涛负责） |
| Preprocess (C) | ~143ms | yuyv_resize_planar，6轮优化到头 |
| TPU Forward | ~40ms | 硬件极限 |
| C NMS | ~4ms | preprocess_ops.so |
| 控制决策 | <1ms | PID + 状态机 |
| **总计** | **~200ms** | **驱动优化后预期 5fps** |

### 2.2 李明涛：StarryOS USB UVC 驱动

在 tgoskits 上合入了 UVC 驱动的核心模块：

- uvc 驱动：`uvc_camera.rs`，含 YUYV 格式支持和 DWC2 USB Host 初始化
- V4L2 框架：按 Linux `include/uapi` 实现设备节点层，`/dev/video0` 正常挂载
- vivid 虚拟驱动重构至 `drivers/media/vivid/`
- 用户态工具 `v4l2-test`：v4l2-ctl 交叉编译 + 3 个 V4L2 采集/测试程序，`run.sh` 一键 build/deploy/sdcard

当前 DQBUF 延迟约 255ms（Linux 端 10ms），驱动层优化进行中。

### 2.4 AKA-00 机器人参考架构分析

深度分析了 chenlongos/AKA-00 的完整技术栈：

- **硬件架构**：SG2002 + ESP32-C3（底盘 PWM PID） + ZP10S/STS3215 舵机（UART）
- **控制算法**：5 状态 FSM（chase→position→grab→bucket→release）+ P 比例差速控制
- **通信协议**：ESP32 UART 帧协议（0xAA 0x55 + checksum），ZP10S ASCII 协议
- **Web 前端**：React + TypeScript，支持方向键/RC 摇杆/重力感应/模型商店

### 2.6 板上模型对比

AKA-00 Linux 系统上，两款 cvimodel 各跑 200 次 TPU Forward：

```
V2        avg=39.6ms  p50=39.5ms  min=39.5ms
AKA-00    avg=188.5ms  p50=188.4ms  min=188.3ms
```

| 模型 | Forward | 内存占用 | Anchors | 检出置信度 |
|------|:---:|:---:|:---:|:---:|
| V2 | 39.6ms | 2.2MB | 8,400 | 0.95-0.97 |
| AKA-00 | 188.5ms | 10.7MB | 27,600 | 0.85 |

V2 快 4.8 倍，因为 anchor 数为 AKA-00 的 1/3，推理负载更低。检出置信度更高得益于 YUYV native 路径（无 OpenCV JPEG 压缩损失）。

### 2.7 StarryOS vs AKA-00 Linux 对比

| 维度 | StarryOS 方案 | AKA-00 方案 |
|------|------|------|
| 内核大小 | 13MB | Buildroot Linux（几十MB） |
| 推理硬件 | SG2002 TPU（0.5 TOPS） | SG2002 CPU（ONNX Runtime） |
| TPU Forward | 40ms | — |
| CPU 推理 | 14.19s | 14.17s |
| 预处理 | C 143ms | OpenCV ~120ms |
| 检出置信度 | 0.95-0.97 | 0.85 |
| SoC 数量 | 1 片 SG2002 | 2 片（+RK3588） |
| BOM 成本 | ~70 元 | 299 元 |

**关于 StarryOS vs Linux 速度对比的更正**：此前曾表述 "StarryOS TPU 推理比 Linux 快"，该结论存在误导。本周在 AKA-00 Linux 板上实测验证后发现：

- TPU 纯 Forward 耗时与 OS 无关。同一模型（V2 cvimodel）在 StarryOS 上 39.6ms，在 AKA-00 Linux 上同样约 40ms。TPU 是独立硬件加速器，推理速度由模型结构和芯片规格决定，不受 Host OS 影响。
- 此前 Linux 端 200ms 的数据来自 Sipeed Buildroot + cvitek_tpu SDK 旧版本，差距源于 SDK 调用链路，而非 Linux 本身。
- 真正体现 OS 差异的是驱动程序成熟度：Linux 端 USB UVC DQBUF 仅 10ms，StarryOS 端当前 255ms。这是 StarryOS 作为较新的自研内核需要追赶的地方，而非推理环节。

### 2.8 预处理 6 轮优化总结

| 版本 | 方案 | Pre 耗时 | TPU 耗时 | FPS | 备注 |
|------|------|:---:|:---:|:---:|------|
| v1 | v3.0 malloc版本 + 串行 | 235ms | 51ms | 2.4 | 基线 |
| v2 | v4 融合版（消除 malloc） | 143ms | 79ms | 2.8 | 消除 921KB malloc |
| v3 | v4 融合版 + 双线程 | 216ms | 195ms | 3.1 | 单核 GIL 争抢，无效 |
| v4 | v5 定点数 + 直写 TPU | 171ms | 88ms | 2.5 | 定点除法比 FPU 慢 |
| v5 | v6 浮点 + 直写 TPU | 143ms | 79ms | 2.8 | 回到浮点 |
| **v6** | **v6 浮点 + 零拷贝** | **143ms** | **40ms** | **2.8** | **当前版本** |

当前 143ms 为纯 C 在 RISC-V 1GHz 单核上的实测结果，进一步优化需要向量化或 DMA。
